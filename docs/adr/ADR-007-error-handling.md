# ADR-007: Error Handling Strategy

## Status
Accepted

## Context
FusionRouter processes LLM requests through a multi-stage pipeline (context assembly, planning, compilation, scheduling, execution, telemetry). Each stage can fail independently, and failures must be surfaced to API clients with appropriate HTTP status codes while preserving enough context for debugging. Early error handling was ad-hoc, using `anyhow::Error` throughout, which made it impossible to distinguish error categories at the boundary.

## Decision

### 1. Centralized `RouterError` Enum

A single `RouterError` enum in `src/types/error.rs` covers all pipeline-level errors:

- `StageFailure` — a named pipeline stage failed with a message
- `ResourceExhausted` — quota limits hit (daily cost/tokens, concurrency)
- `CapacityExceeded` — router-wide saturation
- `ClientCancelled` — client disconnected mid-request
- `BudgetExceeded` — per-request budget envelope exceeded (cost, tokens, iterations)
- `MaxIterationsExceeded` — loop safety limit hit
- `Internal` — unexpected internal errors

### 2. `PipelineStage` Enum

Stages are modelled as a separate enum with `Display` impl, enabling error messages like `"[req-id] Stage 'Execution' failed: provider timeout"`.

### 3. HTTP Status Code Mapping

`RouterError::status_code()` maps each variant to an appropriate HTTP status:
- `StageFailure`, `Internal` → 500
- `ResourceExhausted`, `BudgetExceeded`, `MaxIterationsExceeded` → 429
- `CapacityExceeded` → 503
- `ClientCancelled` → 400

### 4. Domain-Specific Error Types

Separate error enums for subsystems, using `thiserror` for derive macros:
- `CompilerError` — validation errors, pass failures, internal compiler errors
- `SchedulerError` — node failures, cyclic dependency detection
- `BudgetExceededError` — cost, token, and iteration budget caps
- `TransportError` — network, serialization, and transport-level failures

### 5. Layered Error Handling

- `anyhow::Error` used internally within subsystems for flexibility
- Domain error enums wrap specifics at subsystem boundaries
- `RouterError` is the final envelope at the HTTP boundary
- `CompilerDiagnostic` provides structured warnings during compilation (non-fatal)

### 6. Request-ID Correlation

All `RouterError` variants carry a `request_id: Uuid` to correlate errors across logs and traces. The request ID is generated by the `request_id_middleware` and threaded through the pipeline.

## Consequences

- API clients receive consistent, semantically meaningful HTTP status codes
- Debugging is easier with request-ID-tagged error messages
- Subsystems remain decoupled — they use `anyhow` internally and convert to domain errors at boundaries
- Adding a new error variant requires changes in only the enum, Display impl, and status_code mapping
- `anyhow`'s context chaining is preserved inside subsystems but stripped at the boundary
