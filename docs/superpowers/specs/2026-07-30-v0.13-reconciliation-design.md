# FusionRouter v0.13 Reconciliation Design

## Purpose

This specification bridges the frozen FusionRouter v0.13 architecture and the current v0.12-era implementation. It defines how to reconcile architectural drift before new v0.14 Compiler Core feature work begins.

The reconciliation is documentation-first and contract-first. It must not start with source refactoring. The goal is to preserve working v0.12 functionality while making the architecture boundaries explicit enough for safe v0.14 implementation.

## Current Assessment

The current codebase already contains substantial pieces of the v0.13 architecture:

| v0.13 concept | Existing implementation candidates | Assessment |
|---|---|---|
| Normalized Intent | `src/types/mod.rs`, `src/types/execution.rs`, `src/requirements/extractor.rs` | Partial; split across types and currently provider-aware. |
| Workflow IR | `src/types/execution.rs`, `src/types/mod.rs`, `src/planner/` | Partial; good structural seed, but carries concrete model/provider data. |
| Compiler passes | `src/compiler/`, `src/compiler/passes/` | Mostly reusable; pass purity and provider coupling need review. |
| PrimitiveGraph | `src/compiler/ir/primitive_ir.rs` | Good internal lowered representation; should remain compiler-internal. |
| Execution graph/runtime | `src/types/execution.rs`, `src/scheduler/`, `src/executor/` | Reusable runtime pieces, but not yet a v0.13 Execution ABI plus ERI boundary. |
| Capability Registry | `src/capability/registry.rs`, `crates/fusion-plugin-api/` | Mostly aligned; resolver/lowerer placement is the main drift. |
| Capability runtime/package/operations | `src/runtime/`, `src/package/`, `src/operations/` | Useful v0.12 platform work; must be reclassified under v0.13 runtime/plugin/package boundaries. |

The primary architectural drift is provider concern leakage before the Runtime boundary. Frozen v0.13 requires this order:

```text
Intent -> Workflow IR -> Compiler -> Execution ABI -> Execution Target -> Runtime -> Provider Resolution -> Execution
```

Any model, provider, endpoint, or transport decision above Runtime violates that boundary unless it is represented only as a provider-independent constraint.

## Target Architecture

The reconciled codebase must expose six canonical contracts:

1. `NormalizedIntent` — canonical provider-free intent, goals, constraints, policies, budget, and session context.
2. `WorkflowIR` — provider-independent logical workflow, immutable after planning.
3. `ExecutionABI` — stable executable contract emitted only by the compiler ABI generator.
4. `ExecutionTarget` — provider-independent runtime placement and environment constraints.
5. `ExecutionRuntimeInterface` — stable runtime contract for executing ABI graphs.
6. `CapabilityRegistry` — provider-independent semantic capability catalog.

Existing implementation details may remain temporarily behind compatibility adapters, but public architecture should name and document these six contracts consistently.

## Architectural Decisions

### Decision 1: PrimitiveGraph Remains Compiler-Internal

`PrimitiveGraph` must not become the public Execution ABI v1.

The compiler pipeline should be:

```text
WorkflowIR -> PrimitiveGraph -> compiler passes -> ABI Generator -> ExecutionABI
```

Rationale:

- Keeps compiler internals free to evolve.
- Lets `ExecutionABI` remain stable and versioned.
- Matches the frozen architecture, where only the compiler may generate the ABI.
- Avoids turning an optimization/lowering representation into a runtime contract.

Required follow-up: write an ADR that records this decision and rejects the alternative where `PrimitiveGraph` is exposed directly as `ExecutionABI`.

### Decision 2: Compatibility Before Removal

Legacy v0.12 contracts should be adapted before they are removed. The reconciliation path is:

```text
Freeze Contracts -> Compatibility Layer -> Incremental Refactor -> Remove Legacy
```

Adapters are temporary and must be tracked with explicit removal criteria.

### Decision 3: Provider Binding Is Runtime-Owned

Provider/model/endpoint selection belongs behind Runtime and Provider Resolution. Earlier layers may express capabilities, traits, constraints, budgets, and quality preferences, but not concrete providers or model names.

## Workstream A: Documentation Freeze

Goal: make documentation authoritative before source movement.

Deliverables:

- Update `.memory/VERSION` to v0.13.0.
- Update `.memory/overview.md`, `.memory/architecture-map.md`, and `.memory/roadmap.md` to reflect the frozen v0.13 architecture.
- Refresh `.memory/module-index.md` to include `src/runtime/`, `src/package/`, and `src/operations/`.
- Mark `docs/superpowers/plans/2026-07-30-v0.12-*.md` as historical implementation plans, not active instructions.
- Update `.memory/adrs.md` with any new reconciliation ADRs.
- Run `python scripts/check-memory.py` after `.memory/` edits.

Acceptance criteria:

- `.memory/` no longer presents v0.11 or v0.12 as current.
- The six v0.13 contracts are named consistently across memory docs.
- Historical v0.12 plans cannot be mistaken for active implementation plans.

## Workstream B: Contract Freeze

Goal: define canonical contracts without changing behavior.

Deliverables:

- Specify `NormalizedIntent` fields and their mapping from existing `Intent`, `ExecutionIntent`, and `Requirements`.
- Specify provider-free `WorkflowIR` fields and allowed node/edge kinds.
- Specify `ExecutionABI` v1 envelope, node schema, edge schema, versioning rules, and serialization guarantees.
- Specify `ExecutionTarget` fields for environment, resource limits, network constraints, security profile, and scheduler preference.
- Specify `ExecutionRuntimeInterface` methods and lifecycle semantics.
- Confirm `CapabilityRegistry` remains the canonical registry, with resolver placement moved out of planner ownership.

Compatibility layer outputs:

- `WorkflowIRV12 -> WorkflowIR` adapter.
- `ExecutionGraph -> ExecutionABI` adapter.
- Provider/model fields mapped into provider-independent constraints where possible.

Acceptance criteria:

- Contract docs explain how every existing v0.12 type maps to a v0.13 contract or legacy-only category.
- No source behavior changes are required to complete this workstream.

## Workstream C: Boundary Reconciliation

Goal: move responsibilities to match the frozen architecture.

Planned moves:

| Current responsibility | Current location | Target owner |
|---|---|---|
| Capability resolution | `src/planner/resolver/capability/` | `src/compiler/semantic/` or compiler capability pass namespace |
| Capability graph lowering | `src/planner/resolver/capability/lowerer.rs` | Compiler lowering or ABI generation layer |
| Provider/model requirements | `src/types/mod.rs`, `src/requirements/`, compiler model pass | Runtime/provider resolver inputs only; earlier layers use constraints |
| ExecutionGraph as executable contract | `src/types/execution.rs` | Legacy runtime graph or adapter input, not canonical ABI |
| PrimitiveGraph public meaning | `src/compiler/ir/primitive_ir.rs` | Compiler-internal lowered IR |

Boundary rules:

- Planner produces `WorkflowIR` only.
- Compiler is deterministic and side-effect-free.
- Compiler emits `ExecutionABI` through an ABI generator.
- Runtime executes ABI and owns provider resolution.
- Scheduler reads immutable executable work and mutates only runtime state.

Acceptance criteria:

- No planner module produces `ExecutionGraph` or provider bindings.
- No compiler pass performs provider calls, LLM calls, filesystem I/O, or network I/O.
- Provider-specific decisions occur at or below Runtime.

## Workstream D: Compatibility Adapters

Goal: preserve stability while the architecture is corrected.

Adapters:

### Workflow Compatibility

```text
WorkflowIRV12 -> WorkflowIRV13
```

Responsibilities:

- Preserve existing planner output semantics.
- Convert concrete model strings into abstract constraints or legacy annotations.
- Emit diagnostics when information cannot be represented provider-independently.

Removal criteria:

- All planners emit provider-free `WorkflowIR` directly.
- Tests cover legacy workflow fixtures through the new IR.

### Execution Compatibility

```text
ExecutionGraph -> ExecutionABI
```

Responsibilities:

- Allow current scheduler/executor tests to continue while ABI v1 is introduced.
- Preserve node IDs, edges, retry policies, cache policies, security policies, and telemetry hooks where available.
- Make missing ABI fields explicit through defaults or diagnostics.

Removal criteria:

- Compiler emits `ExecutionABI` directly.
- Runtime consumes `ExecutionABI` through ERI.
- `ExecutionGraph` is either retired or explicitly documented as a runtime-private graph.

### Capability Compatibility

Responsibilities:

- Keep existing `CapabilityRegistry` stable.
- Move resolver/lowerer ownership without changing registry behavior.
- Keep package/plugin ABI compatibility until v0.14 replacement points are complete.

Removal criteria:

- Capability resolution pass lives in compiler semantics.
- Runtime performs late provider binding based on resolved capabilities and execution target.

Acceptance criteria:

- Adapters are explicitly marked temporary.
- Adapter tests prove old v0.12 workflows still execute or compile through the new boundary.
- Removal criteria are recorded before implementation begins.

## Workstream E: Compiler Core Preparation

Goal: derive v0.14 implementation from the reconciled architecture.

Recommended sequence:

1. Documentation and ADR updates.
2. Contract type definitions behind compatibility adapters.
3. Provider-free Workflow IR cleanup.
4. PrimitiveGraph cleanup as compiler-internal IR.
5. ABI generator and `ExecutionABI` v1.
6. Capability semantic resolution pass relocation.
7. `ExecutionTarget` definition.
8. ERI definition and local runtime adapter.
9. Legacy adapter removal after tests prove direct v0.14 path.

## Repository Health Requirements

Before major refactoring begins:

- `cargo check` must pass.
- `cargo test` must pass.
- `cargo check --no-default-features --lib` must pass.
- Known warnings that violate repository policy should be triaged, starting with `src/package/format.rs:1:21` unused import `Write`.
- Dirty worktree docs should be intentionally committed or explicitly left uncommitted by the maintainer before broad source movement.

## Out Of Scope

This reconciliation spec does not implement:

- New v0.14 compiler features.
- Source module moves.
- Provider resolver changes.
- Runtime execution behavior changes.
- Plugin ABI removal.
- Distributed runtime features.

Those belong in implementation plans derived after this spec is reviewed.

## Completion Criteria

Reconciliation is complete when:

- `.memory/` is updated and validates with `python scripts/check-memory.py`.
- ADR records that `PrimitiveGraph` remains compiler-internal and `ExecutionABI` is generated separately.
- Canonical contract specs exist for all six v0.13 abstractions.
- Compatibility adapters are specified with tests and removal criteria.
- Provider leakage above Runtime is inventoried and scheduled for removal.
- v0.12 plan files are marked historical.
- Repository verification commands pass with warning status documented.
- A v0.14 Compiler Core implementation plan can be written without re-deciding architecture.
